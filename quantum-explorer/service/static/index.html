Educational guide: how PQ transactions are created, detected, and independently verified.

How a PQ transaction is made (concept)

Step 1: Build a normal Dogecoin transaction with standard inputs/outputs using wallet logic.

Step 2: Attach a post-quantum commitment payload (commonly in OP_RETURN) that references PQ signature/artifact metadata.

Step 3: Broadcast to network. Confirmation and inclusion are visible once the transaction is mined.

This explorer classifies Phase-1 commitments using canonical tagged OP_RETURN format: 6a24 + FLC1/DIL2/RCG4 + 32-byte commitment.

Using Dogecoin Foundation libdogecoin

Recommended project links:

  • libdogecoin repository
  • libdogecoin examples
  • PQC such commands (Falcon-512 / carrier tools) — official-style docs for keygen, falcon_commit, TX construction helpers, and the two-step carrier flow.

Typical workflow is: key management + tx composition in libdogecoin, PQ commitment embedding in tx data, then broadcast/monitoring through node or P2P listeners.

TX_C and TX_R (two-step carrier flow)

Matches the libdogecoin carrier model documented under Falcon-512 PQC commands:

  • TX_C (commitment): includes OP_RETURN with 6a24 + tag (FLC1 / DIL2 / RCG4) + 32-byte commitment, where commitment = SHA256(pqc_public_key ‖ pqc_signature) over the signing message (e.g. tx sighash).
  • Optional carrier P2SH: canonical redeemScript OP_DROP ×5 OP_TRUE holds DOGE until reveal; scriptPubKey is the standard P2SH pattern from pqc_carrier_scriptpubkey.
  • TX_R (reveal): spends the carrier input; Falcon pubkey (~897 B) and signature (~652–666 B) ride in scriptSig using the tagged carrier layout (FLC1FULL / chunking per pqc_carrier_mkpart).

This explorer’s strict check only inspects outputs for the canonical OP_RETURN commitment. When the core indexer has the tx’s block, carrier verification matches SHA256(pk‖sig) from scriptSig to indexed TX_C commitments: all quantum txs with Phase-1 OP_RETURN from block (TX_R height − lookback) through TX_R height, plus any same-block txs (see carrier_phase1 in tx JSON). Tune QE_PQ_CARRIER_COMMITMENT_LOOKBACK_BLOCKS (default 750000) if a TX_C is older than the window. For FLC1, optional Falcon crypto verify (such tx_sighash32 + such falcon_verify, QE_SUCH_PATH) reproduces Core’s signature check when Dogecoin Core RPC can supply the prevout scriptPubKey; see falcon_crypto_verify in tx JSON.

Technical verification anyone can do

  • Fetch raw tx hex (from your node or trusted explorer APIs).
  • Decode outputs and inspect canonical commitment output: OP_RETURN 0x24 <TAG4> <32-byte-commitment>.
  • Verify TAG4 is one of FLC1, DIL2, RCG4.
  • When TX_R carrier data exists, reconstruct pubkey||signature parts and check SHA256(pubkey||signature) against TX_C commitment.
  • For Falcon (FLC1), optionally run the same sighash + falcon_verify path as Dogecoin Core (libdogecoin such with liboqs).
  • Check block inclusion/confirmations via your node or this explorer’s indexed chain.

In this UI, open a tx detail to see decode + strict PQ evidence. External verifiers can reproduce the same parsing from raw bytes.

What "proof" means here

There are two layers:

  • Commitment proof: tx data contains canonical Phase-1 tagged OP_RETURN commitment structure.
  • Chain proof: transaction is seen/confirmed in chain context.

The strict verifier currently proves commitment-level evidence from raw tx bytes. Full cryptographic PQ signature validation can be layered on top as protocol rules evolve.

Explorer APIs useful for auditors

  • /api/public/tx?txid=... — decode + strict evidence
  • /api/public/block?height=... — block context
  • /api/public/status — explorer status snapshot
  • /api/public/metrics — aggregate activity

Auditors can export JSON from these endpoints and independently replay parsing/verification logic.

Important limits and transparency notes

  • Network and sync availability affect how quickly new blocks and txs appear.
  • No raw hex = no strict commitment validation.
  • Only canonical Phase-1 commitment encoding is treated as valid.

For educational integrity, the explorer shows reason/evidence fields instead of hiding uncertain states.
