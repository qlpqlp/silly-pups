menu_bookPost-Quantum Documentation

Educational guide: how PQ transactions are created, detected, and independently verified.

How a PQ transaction is made (concept)

Step 1: Build a normal Dogecoin transaction with standard inputs/outputs using wallet logic.

Step 2: Attach a post-quantum commitment payload (commonly in OP_RETURN) that references PQ signature/artifact metadata.

Step 3: Broadcast to network. The tx is first seen in mempool (pending), later linked to blocks (confirmed).

This explorer classifies PQ state from raw transaction bytes and marker evidence. It is designed for transparent education, so evidence/reason fields are always exposed.

Using Dogecoin Foundation libdogecoin

Recommended project links:

  • libdogecoin repository
  • libdogecoin examples

Typical workflow is: key management + tx composition in libdogecoin, PQ commitment embedding in tx data, then broadcast/monitoring through node or P2P listeners.

Technical verification anyone can do

  • Fetch raw tx hex (from node RPC or explorer APIs).
  • Decode outputs and inspect scriptPubKey + OP_RETURN payload bytes.
  • Check recognized PQ commitment markers and parser result.
  • Check block inclusion/confirmations via chain/SPV context.

In this UI, open a tx detail to see decode + strict PQ evidence. External verifiers can reproduce the same parsing from raw bytes.

What "proof" means here

There are two layers:

  • Commitment proof: tx data contains expected PQ marker structure.
  • Chain proof: transaction is seen/confirmed in chain context.

The strict verifier currently proves commitment-level evidence from raw tx bytes. Full cryptographic PQ signature validation can be layered on top as protocol rules evolve.

Explorer APIs useful for auditors

  • /api/public/tx?txid=... — decode + strict evidence
  • /api/public/block?height=... — block context
  • /api/public/status — runtime/SPV context
  • /api/public/metrics — aggregate activity

Auditors can export JSON from these endpoints and independently replay parsing/verification logic.

Important limits and transparency notes

  • Mempool visibility can vary by peers and network conditions.
  • No raw hex = no strict marker validation.
  • PQ labeling depends on protocol marker conventions configured by implementation.

For educational integrity, the explorer shows reason/evidence fields instead of hiding uncertain states.
